# General task harness

Use one task contract to define a goal, protected requirements, editable files,
checks, agent host and repair limits. The same execution loop supports software,
JSON data, text artifacts and external tool adapters. Each check names an explicit
criterion and whether it contributes to verification (implementation checks) or
validation (the agreed intended outcome).

## Try the checks without an agent

From the Proof Loop checkout, run:

```sh
python3 -B tools/harness_smoke.py
python3 -B proofloop harness-adapters
```

The smoke uses disposable software, data and document examples, checks their
deliberate failures, corrects synthetic fixtures directly and checks again. It
does not call a model. Literal document checks only establish the requested text
conditions; they do not establish that a document is factually correct.

For your own task, copy one example to a new project directory and review its
`task.json` and protected requirements. Then run:

```sh
python3 proofloop harness-check --root /path/to/project --run-id trial --task task.json
python3 proofloop harness-status --root /path/to/project --run-id trial --task task.json
```

`harness-check` executes only checks and records a checkpoint. It cannot dispatch
an agent, including when the next recorded stage is a builder or verifier. Its
exit is 0 only when both verification and validation checks pass; it returns 2
for a failure, uncertainty or invalid contract. It can run without Codex installed.
Use a new run ID if the contract or files were changed outside the harness.

## Run the bounded agent loop

With the native Codex host installed and signed in, use the same contract:

```sh
python3 proofloop harness-run --root /path/to/project --run-id trial --task task.json
python3 proofloop harness-cancel --root /path/to/project --run-id trial
```

The loop runs each check on its own file snapshot and checks it for changes before
the next check starts. Failed criteria route to
configured specialists and then a builder. Only allowlisted proposed UTF-8 file
contents are applied. All criteria run again, followed by a fresh verifier session
on the exact candidate. Verifier findings can start another repair within the
remaining limits. A successful initial check still requires a verifier before
advisory completion. This is a sequential layered workflow; specialist routing is
explicitly configured rather than generated by an unrestricted staffing agent.

`harness-run --max-steps 1` creates a checkpoint after at most one stage. Resume
the same command after inspecting status. Unfinished stages, uncertain process
outcomes, malformed external protocols and exhausted budgets stop work. Failed
checks and previous file contents remain in the run evidence. No command wakes
itself or schedules future work.

## Task contract

The [schema](schemas/harness-task.schema.json) describes version 1. Runtime
validation additionally checks path containment and cross-field relationships.
Unknown fields, duplicate JSON keys, nonfinite numbers and unknown adapters fail
before a run is created.

- `goal`: observable intended result.
- `files`: exact files available to checks and agents. Every dependency must be
  included; there is no automatic import discovery or package installation.
- `editable` and `protected`: disjoint subsets of `files`. Requirements and all
  declared files under unittest directories must be protected. The contract
  itself is always frozen. Prospective missing files must be editable.
- `requirements`: nonempty list of protected requirement files.
- `checks`: 1–16 uniquely named checks, including at least one verification
  criterion and one validation criterion. All checks are required.
- `specialists`: up to two roles with instructions and `quality_failure` and/or
  `verification_failure` triggers. They diagnose failures and cannot approve work.
- `host`: `{"kind":"codex"}` or an explicitly configured local command host.
- `limits`: explicit `max_repairs` (0–2), `max_agent_calls` (1–12),
  `agent_timeout_seconds` (1–600), `check_timeout_seconds` (1–300), and
  `max_run_seconds` (1–1800). Total elapsed time persists across checkpoints.

The inherited file scope is at most 200 files and 2 MiB of initial contents.
Deletion, renaming and binary proposals are unsupported. These are bounded local
tasks; larger projects need a deliberately selected file scope or an external
adapter. Builders cannot enlarge these limits or change criteria mid-run.

## Check adapters

| Adapter | Contract | What a pass establishes |
| --- | --- | --- |
| `json-equals` | `path`, `assertions` containing `pointer` and `equals` | Exact typed JSON values at RFC 6901 pointers; booleans and numbers differ |
| `text` | `path`, `contains`, `excludes` | Required literal text is present and forbidden literal text is absent |
| `python-unittest` | `start_dir`, `pattern`, frozen `test_ids` | Every declared matching Python test module runs; executed test IDs exactly match the approved list; no failures, errors, skips, expected failures or unexpected successes |
| `command-json` | Explicit `argv`, protected `controls`, expected `coverage` | The configured trusted tool's scoped result and coverage agree with the contract and exit |

Text assertions cannot both be empty. JSON arrays use zero-based indices.
JSON observations retain typed-value hashes rather than duplicating large values.
Each serialized check report is bounded to 256 KiB; oversized reports stop the
run and preserve the failed stage evidence.
Missing or malformed candidate artifacts fail their checks. Protected Python
tests run in a fresh process with an observed structured test summary. Commands
run without a shell added by the harness. `{python}` expands to the current
interpreter and `{workspace}` to the stage snapshot.

The unittest adapter compares executed module names against every declared
matching `.py` file under the test directory. It fails if discovery omits a
declared module, even when another test passes. Nested directories must be
discoverable by unittest, normally with protected `__init__.py` files. A module
that intentionally contributes no test fails the coverage rule. The `test_ids`
list freezes the complete set of agreed unittest IDs, such as
`test_add.Addition.test_positive`; missing, unexpected or duplicate executions
fail, including tests omitted by a `load_tests` hook. Review the IDs and tests
before approving the task. This check does not prove that the approved list
covers every intended scenario.

An external check receives one JSON request on stdin with `schema_version`,
`check_id`, `criterion`, `purpose` and the expected `coverage`. It must print only one JSON result to stdout;
diagnostics can go to stderr. A passing response and exit 0 look like:

```json
{"schema_version":1,"check_id":"my-check","state":"pass","findings":[],"coverage":["Declared acceptance cases"]}
```

A failure must use `state: "fail"`, nonempty findings and a nonzero exit. Coverage
must exactly match the nonempty coverage list frozen in the check contract.
Missing results, skipped/unknown states, partial coverage, mismatched identities,
duplicate keys and exit/result disagreements stop as uncertain protocol evidence.
This interface lets other language test runners, artifact tools and domain tools
participate without changing the orchestration loop. A wrapper must faithfully
translate its tool's failures, skips, partial execution and coverage. List the
wrapper, configuration and criterion dependencies in `controls`; every listed
control must be a declared protected file. Dependency completeness is an
operator responsibility; the harness cannot infer arbitrary program dependencies.

## Agent host interface

The default `codex` host reuses the existing [native protocol adapter](AGENT-BRIDGE.md).
To integrate another local agent runner, configure:

```json
{"kind":"command","argv":["{python}","agent_adapter.py"],"controls":["agent_adapter.py"]}
```

Host `controls` must likewise be declared protected files. Installed provider
binaries and credentials remain under operator control outside the task.
Every role launches a fresh process. Stdin contains `protocol_version: 1`, a fresh
`request_id`, `role`, `candidate_sha256`, `response_schema` and the frozen `prompt`.
The adapter must return exit 0 and exactly one JSON object with the same protocol,
request, role and candidate fields, plus a nonempty unique `session_id` and
`response` matching the supplied role schema. Builders return complete proposed
file contents; specialists return findings; verifiers return a candidate-bound
verdict and findings. A passing verifier must have no findings. Reused session
identities are rejected. Raw requests, responses, process outcomes and cleanup
records remain in the stage evidence.

The adapter is responsible for actually creating fresh provider sessions. A
self-reported session ID is attribution, not authenticated independent identity.
The harness does not provision credentials, install a provider or select a model
by guessing from a role name. Configure providers and role/model routing in your
operator-controlled adapter. Normal runtime permissions govern the adapter.

## Results and trust

Results show `verification` and `validation` separately, including the checked
criteria and failed IDs. `completed_advisory` requires all criteria and the fresh
verifier to pass. Every result retains `acceptance: not_accepted`. The original
portable receipt validator is unchanged; new check reports are not relabeled as
its Verified evidence. Passing criteria means the declared criteria passed. An
incomplete specification can still miss a real requirement.

`harness-status` is a dedicated read-only reader: it creates no lock, database,
workflow or processes. It checks the task, source files, completed stages and
nested evidence; changing state or active work makes freshness indeterminate.
Stale outcomes remain historical. Exit 0 means the inspection is stable and
current, even for a blocked run; exit 2 means stale, indeterminate or unreadable.
After a builder changes the candidate, checks from the prior candidate are marked
historical and current verification/validation are unset until checks run again.
An interrupted journaled promotion can be inspected with `harness-status` and, after
reviewing the files and evidence, completed without new agent calls using
`harness-recover --root PROJECT --run-id RUN --task task.json --finish-promotion`.
Pause other writers during promotion and recovery; the source comparison and replacement
are separate operations.
Pre-repair draft runs lack candidate binding and module/case coverage: status can
show their recorded checks as unbound historical evidence, but they cannot resume
as current work. Add the agreed `test_ids` to unittest checks and start a new run
ID with the repaired harness; retain the old contract to inspect old evidence.

Snapshots and protected files detect ordinary unauthorized changes. They are not
an OS sandbox, authenticated proof, malicious-code containment or independent
custody. Test code and external adapters execute on a trusted local host and can
access resources allowed by that host. Use separately controlled requirements,
runtime isolation and human decisions where the task requires them.

The new integration tests use real local subprocesses with explicitly synthetic
agent fixtures. They establish protocol handling and bounded orchestration, not
live model performance or cross-platform qualification.
